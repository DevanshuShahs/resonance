# AI Music Discovery Engine (Resonance)

## Context

Resonance currently has a synthetic ~5,000-track catalog (`data/tracks.csv`) loaded and validated into SQLite (`db/resonance.db` via `scripts/schema.sql` / `scripts/load_and_validate.py`). The next step is to make that catalog actually searchable by meaning: given a natural-language query like *"upbeat happy pop songs for a road trip"*, return highly relevant tracks by combining semantic vector similarity with relational (SQL) filtering.

The explicit goal is to demonstrate real information-retrieval technique and hand-built data structures/algorithms rather than reach for a vector-search library. Three architectural decisions were confirmed with the user up front:

1. **Embeddings**: pretrained sentence-transformer (MiniLM) text embeddings, concatenated with normalized audio features.
2. **ANN index**: a from-scratch random-hyperplane LSH index (not FAISS/hnswlib/annoy).
3. **Interface**: a FastAPI REST API (`POST /search`), not just a CLI.

This plan also fixes two correctness gaps that matter in practice: what happens when SQL filters are too restrictive (must degrade gracefully, never return empty), and what happens if the embedding artifacts and the DB ever drift out of row-order alignment (must fail loudly at startup, never silently misattribute a vector to the wrong track).

## Recommended approach

### Layout

```
engine/                      # framework-agnostic IR core (no FastAPI import)
  vocab.py                   # GENRES, MOODS, GENRE_SYNONYMS, MOOD_AUDIO_HINTS (shared w/ generator)
  config.py                  # all tunable constants, single source of truth
  text_descriptor.py         # semantic_text() + lexical_tokens() per track
  audio_norm.py               # compute/apply/persist min-max stats
  embeddings.py               # SentenceTransformer wrapper + vector composition
  lsh_index.py                 # LSHIndex: build/save/load/query w/ multiprobe + fallback
  inverted_index.py            # InvertedIndex: build/save/load/bm25_scores
  query_parser.py               # rule-based NL -> ParsedQuery (genres/moods/audio_filters/raw_text)
  sql_filters.py                 # ParsedQuery -> SQL WHERE + relaxation ladder
  store.py                        # EngineStore: loads all artifacts + DB once, alignment guard
  search.py                        # orchestrates full pipeline -> ranked results
api/
  schemas.py                  # SearchRequest / SearchResult / SearchResponse (pydantic)
  routes.py                    # POST /search
  main.py                       # FastAPI app + lifespan startup builds one EngineStore
artifacts/                    # generated by build script, gitignored
  embeddings.npy, track_ids.json, norm_stats.json, hyperplanes.npy, buckets.json, inverted_index.json
scripts/
  build_embeddings.py         # NEW: offline build of all artifacts/ from the DB
  bench_ann.py                # NEW: LSH vs brute-force latency/candidate-count benchmark
  smoke_test.py                 # NEW: in-process NL query sanity check
requirements.txt              # NEW
```

`scripts/generate_dataset.py` is lightly refactored: its `GENRES`/`MOODS` constants and the mood/audio heuristic inside `make_mood_tags` move into `engine/vocab.py` (`MOOD_AUDIO_HINTS`), imported back into the generator, so the query parser and the data generator share one definition instead of two independent copies.

### Algorithm design

**Semantic text descriptor** (`engine/text_descriptor.py`): built from genre + mood_tags only, e.g. `"pop music that feels happy, uplifting"`. Title/artist are synthetic random names with no real semantic content, so they're excluded from the embedding (would just add noise) but are indexed lexically instead, alongside genre and mood tags, for BM25.

**Audio feature vector**: the 9 continuous features (danceability, energy, valence, tempo, loudness, speechiness, acousticness, instrumentalness, liveness) are min-max normalized using stats computed once at build time and persisted to `norm_stats.json`, so query-time normalization always matches. `duration_ms`, `key`, `mode`, `time_signature`, `popularity` are excluded from the vector (categorical / ranking-signal, not mood).

**Vector composition**: 384-d text embedding and 9-d audio vector are each unit-normalized, weighted (`TEXT_WEIGHT=0.6`, `AUDIO_WEIGHT=0.4`), concatenated to 393-d, then L2-normalized again so cosine similarity reduces to a dot product. At query time, if the parser found no mood/adjective signal, the audio sub-vector is all zeros (contributes nothing) rather than a "neutral 0.5" that would bias every match toward average audio features.

**Custom LSH index** (`engine/lsh_index.py`): random-hyperplane LSH, `L=8` tables x `k=12` hyperplanes, hyperplanes generated once (seed 42) and persisted to `hyperplanes.npy` so build/query never drift. Query unions candidate buckets across all `L` tables; if fewer than `MIN_CANDIDATES` are found, widens via Hamming-neighbor multiprobe (radius 1, then 2); if still short, the caller falls back to brute-force cosine over the current pool (bounded by any active SQL allowlist, so cheap even at large catalog sizes). Built exclusively offline by `scripts/build_embeddings.py` — the API only ever loads a persisted index, never builds one at startup. `config.py` documents the scaling knob: increase `k` with `log2(N)` and `L` for recall as the catalog grows.

**Custom inverted index + BM25** (`engine/inverted_index.py`): hand-built postings list (`term -> [(doc_idx, tf)]`), standard BM25 (`k1=1.5, b=0.75`), scored only over the candidate set already produced by SQL+ANN — never a full-corpus scan at query time.

**Rule-based NL query parser** (`engine/query_parser.py`): no LLM call. Tokenizes the query and matches against `engine.vocab` genres/synonyms and moods, plus a local `ADJECTIVE_RULES` table (upbeat/chill/sad/fast/slow/acoustic/instrumental/danceable/loud/quiet -> audio-feature thresholds). Mood matches also contribute their `MOOD_AUDIO_HINTS` threshold. The full raw query string is always kept, untouched, for the semantic embedding.

**Relational filtering <-> ANN pipeline** (`engine/search.py`): SQL runs first as a prefilter, walking a relaxation ladder if the result is too small — `full filters -> filters minus audio thresholds -> genre only -> unrestricted`. Any predicate dropped during relaxation is remembered and becomes a small score bonus for candidates that happen to satisfy it anyway, so an over-restrictive query degrades gracefully instead of returning nothing. ANN candidates are then intersected with the (possibly relaxed) allowlist, with brute-force fallback as described above. BM25 scores the same candidate pool. Final score: `0.65*cosine + 0.25*bm25_norm + 0.10*popularity_norm + relaxation_bonus`, top-K via `heapq.nlargest`.

**Alignment guard** (`engine/store.py`): `build_embeddings.py` writes tracks in `ORDER BY id` and records that exact id order in `track_ids.json`. `EngineStore` at API startup reloads tracks in the same order and asserts the ids match exactly, failing loudly instead of silently mismatching vectors to tracks if the DB was reloaded without rerunning the build script.

### Setup and dependencies

`requirements.txt`: `sentence-transformers`, `torch`, `numpy`, `fastapi`, `uvicorn[standard]`, `pydantic`. No FAISS/hnswlib/annoy/scikit-learn — numpy is used only for array math, never as a vector-search library.

**Real prerequisite to verify first, before writing code**: this environment currently has zero Python packages installed and no venv. Installing `sentence-transformers` pulls in `torch` (large CPU wheel, ~1-2GB venv footprint) and the first run of `build_embeddings.py` downloads the MiniLM model (~80MB) from Hugging Face — both require internet access. This should be checked (`pip install` a small package, or just attempt the real install) as the first implementation step; if this sandbox has no internet access at all, that's a hard blocker for the pretrained-embedding approach and needs to be flagged back before continuing, not discovered mid-build.

### Build/run sequence

1. `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
2. `python scripts/load_and_validate.py` (already done; idempotent, safe to rerun)
3. `python scripts/build_embeddings.py` — reads `tracks`, builds descriptors/audio vectors, embeds, builds LSH + inverted index, writes `artifacts/`
4. `python -m uvicorn api.main:app --reload --port 8000`
5. `curl -X POST localhost:8000/search -H 'Content-Type: application/json' -d '{"query":"upbeat happy pop songs for a road trip","top_k":10}'`

## Verification

- **`scripts/smoke_test.py`**: runs ~8 canned NL queries in-process (no HTTP) chosen to exercise every pipeline branch — genre+adjective combos, mood-only vibes, unrecognized-genre (tests the relaxation ladder), and nonsense input (tests pure-semantic fallback). Prints parsed filters, applied filter level, and top-10 results with score breakdown for manual relevance eyeballing. This is qualitative — the synthetic dataset has no human relevance labels, so there's no automatic precision/recall ground truth.
- **`scripts/bench_ann.py`**: times the custom LSH query against brute-force cosine over the full matrix, reporting latency, candidates-examined (LSH should be dramatically fewer), and top-K overlap (Jaccard) to confirm LSH approximates brute-force ranking. At N=5,000 a single BLAS matmul may already be sub-millisecond, so the benchmark should honestly report that wall-clock may not show a dramatic win yet — the meaningful metric is candidates-examined, which is the axis that diverges as the catalog grows.
- **Optional larger-scale check**: rerun `generate_dataset.py --rows 50000`, load into a second DB, rebuild artifacts, rerun the benchmark to make the wall-clock crossover visible at real scale.
- Manual end-to-end: hit the running API with `curl` for a handful of real queries and eyeball result relevance and response shape.
